# 개발자 검토와 정식 버전 기준

## 검토 요청

아키텍처 제안의 모호함, 실무 적용 시 깨지는 조건, 비개발자가 AI에게 전달할 때 발생할 오해를 찾고 있습니다. 문제가 있는 문장과 구체적인 실패 사례, 가능하면 대안을 함께 제시해 주세요.

1. 고유 업무 규칙과 어댑터의 경계가 충분히 명확한가요?
2. 외부 서비스별 인증과 데이터 소유권에서 빠진 판단이 있나요?
3. 연결을 끊거나 교체할 수 있다는 설명이 실제 가능 범위를 과장하나요?
4. 기존 도구 채택보다 직접 구현이 나은 조건을 충분히 설명하나요?
5. 단일 호스트의 Docker 구성이 가진 공유 장애를 제대로 설명하나요?
6. 선택 사항이 필수 구성처럼 읽히는 부분이 있나요?
7. AI가 이 문서를 따라 과도한 서비스 분리나 불필요한 내부 에이전트를 도입할 여지가 있나요?

## 초안에서 정식 버전으로

- 이슈별로 수용·수정·보류와 이유를 기록합니다.
- 원칙 변경은 관련 문서와 시작 지시문에 함께 반영합니다.
- 한 가지 예시 프로젝트로 요구 분석·선정·설계 흐름을 끝까지 수행해 문서의 사용성을 확인합니다.
- 최소 연결 구현으로 정상 동작과 서비스 중단 시 동작을 확인하고, 사용 버전과 결과를 공개합니다.
- 남은 한계와 미검증 영역을 기록합니다.
- 위 결과를 반영한 뒤 v1.0.0 태그와 릴리스 설명을 발행합니다.

현재 항목들은 완료되지 않았습니다. 초안 공개, 피드백 모집, 정식 버전 발행을 구분합니다. 피드백 수만으로 검증 완료를 선언하지 않습니다.
