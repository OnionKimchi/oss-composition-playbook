# 아키텍처 제안

## 1. 목표와 적용 범위

개발 리소스가 제한된 프로젝트에서 기존 오픈소스의 기능을 활용하고, 직접 작성해야 하는 코드를 고유한 업무 로직과 통합 코드에 집중시키는 것이 목표입니다. 특히 AI 코딩 도구에 구조적 방향을 전달하는 것을 목적으로 합니다.

메인 백엔드가 업무 흐름을 소유하고, 외부 기능은 독립 실행되는 소프트웨어에 위임합니다. 서비스의 개수나 특정 제품 목록을 먼저 정하지 않습니다. 오픈소스 채택 여부는 실제 요구와 통합·운영 비용으로 결정합니다.

## 2. 구성 요소와 책임

| 요소 | 책임 | 경계 |
| --- | --- | --- |
| 프론트엔드 | 사용자 입력·결과 표시 | 외부 서비스의 관리자 자격 증명을 보유하지 않음 |
| 메인 백엔드 | 인증·인가 적용, 고유 업무 규칙, 서비스 연결 조율 | 외부 서비스의 내부 DB 구조에 직접 의존하지 않음 |
| 어댑터 | API 호출, 인증 전달, 데이터·오류 변환, 호출 제한 | 고유 업무 규칙과 외부 API 형식의 혼합을 줄임 |
| 독립 서비스 | 채택한 오픈소스가 제공하는 기능 | 제공 API와 명시된 데이터 교환 경로로 연결 |
| 개발용 AI | 요구 분석, 선정안 작성, 구현, 검증 | 운영 서비스의 상시 구성 요소로 간주하지 않음 |
| 내부 AI 에이전트 | 필요할 때 자연어 해석·도구 선택 등 | 선택 사항이며 허용된 백엔드 기능만 호출 |

어댑터는 우선 메인 백엔드 내부 모듈로 둘 수 있습니다. 어댑터마다 별도 컨테이너나 별도 서버를 만드는 것은 필수가 아닙니다.

## 3. 필수 원칙

이 절의 필수는 본 제안을 채택하는 프로젝트의 설계 원칙을 뜻합니다.

1. **기존 도구 우선 검토.** 요구를 충족하는 후보를 조사하고, 채택·미채택 이유를 남깁니다. 후보가 없거나 통합 비용이 더 크면 직접 구현합니다.
2. **외부 기능은 명시적인 경계로 연결.** 공개·지원 API를 우선 사용합니다. 외부 DB 직접 접근이나 비공식 인터페이스가 필요하면 예외로 기록하고 교체·업그레이드 영향을 밝힙니다.
3. **고유 업무 규칙의 소유권 유지.** 프로젝트의 핵심 정책과 외부 서비스별 변환 코드를 구분합니다. 외부 서비스에 규칙을 두는 경우 그 의존성을 기록합니다.
4. **데이터 소유권 명시.** 엔터티별 원본 시스템, 외부 ID 매핑, 복제 범위, 삭제·이전 절차를 정합니다. 여러 시스템의 같은 필드가 동시에 원본이 되지 않게 합니다.
5. **실패 동작 명시.** 연결 실패가 사용자에게 미치는 영향, 요청 시간 제한, 재시도 가능 여부, 중복 방지, 복구 방법을 정의합니다.
6. **구현과 검증 구분.** 코드가 존재한다는 이유로 정상 동작을 주장하지 않습니다. 수행한 검증과 미검증 항목을 기록합니다.

## 4. 기본 권장 사항

- 단일 호스트에서는 Docker Compose로 메인 백엔드와 채택 서비스를 실행하는 구성을 기본으로 제안합니다. 이미지 버전과 영속 볼륨을 명시합니다.
- 외부 도구의 소스를 대규모 수정하기 전에 설정·플러그인·API 확장 가능성을 검토합니다. 수정이 필요하면 유지보수 책임과 업스트림 추적 방식을 기록합니다.
- 서비스 내부 통신과 공개 접근을 구분하고 필요한 접점만 외부에 노출합니다.
- 로그에는 요청을 추적할 식별자를 남기되 인증 정보와 민감한 원문을 기록하지 않습니다.
- 백업과 복구는 메인 DB뿐 아니라 각 서비스의 데이터·첨부 파일·설정도 대상으로 삼습니다.

호스트 OS 접근, 장비 제어 등 컨테이너 밖 실행이 필요한 경우에는 예외와 연결 경계를 명시합니다.

## 5. 사용자와 결정할 선택 사항

| 항목 | 판단 기준 |
| --- | --- |
| 서비스 내부 AI 에이전트 | 자연어 판단이 필요한지, 정해진 규칙으로 충분한지 |
| Codex CLI / App Server의 서비스 내부 사용 | 지원되는 실행·인증 방식, 운영 적합성, 비용·권한을 별도 확인 |
| 로컬 모델 / 클라우드 모델 | 처리량, 장비, 응답 시간, 데이터 취급, 운영 비용 |
| 동기 API / 비동기 작업 | 작업 시간, 즉시 결과 필요성, 실패 복구 요구 |
| 별도 메시지 브로커 | 전달 보장과 작업량이 단순 백엔드 작업 처리로 충족되는지 |
| 서비스별 별도 DB 서버 | 제품 요구와 자원·운영 비용. 데이터 소유권 분리는 서버 수와 별개 |
| 배포·개발 환경 분리 수준 | 서비스 영향, 예산, 가용성 요구 |

서비스 내부 Codex 도입은 Docker와 같은 기본 배포 권장 사항으로 취급하지 않습니다. 외부 개발용 Codex 사용과 내부 실행의 인증·과금·수명주기를 동일하다고 가정하지 않습니다. 이 문서는 구독이나 인증의 재사용 가능성을 보장하지 않습니다.

## 6. 연결 중단과 교체

“문제 있는 서비스를 끊을 수 있다”는 것은 의도적으로 경계를 설계한다는 뜻입니다. 모든 기능이 계속 작동하거나 데이터가 자동 이전된다는 뜻은 아닙니다.

예를 들어 문서 검색 서비스가 중단되면 문서 등록은 유지하고 검색만 제한할 수 있습니다. 반면 필수 결재 엔진이 중단되면 승인 완료 처리를 멈춰야 할 수 있습니다. 두 상황을 같은 방식으로 처리하지 않습니다.

각 어댑터에 다음 내용을 기록합니다.

- 담당 기능과 필수·선택 의존성
- 요청·응답 계약과 지원 버전
- 제한 시간과 동시 호출 한도
- 오류 분류와 재시도 조건: 쓰기 재시도는 멱등 키나 결과 조회 등 중복 방지 수단 확인
- 연결 해제 시 UI·업무 흐름의 동작
- 데이터 내보내기, 대체 서비스 ID 매핑, 재연결 절차

별도 컨테이너라도 같은 호스트의 CPU·메모리·디스크·네트워크 장애를 공유할 수 있습니다. 자원 한도와 상태 점검은 운영 환경에 맞춰 검증합니다.

## 7. 한계와 비용

이 방식은 자체 구현량을 줄일 수 있지만 인증 통합, 데이터 동기화, API 변경 대응, 라이선스 확인, 백업, 업그레이드와 관측 비용을 추가합니다. 메인 백엔드가 모든 서비스의 세부 모델을 그대로 노출하면 결합이 다시 커집니다.

작은 단일 기능이나 매우 짧은 지연이 필요한 흐름에서는 직접 구현이 유리할 수 있습니다. 하나의 업무를 여러 서비스가 수정할 때에는 부분 성공과 데이터 불일치를 어떻게 복구할지 결정해야 합니다. API를 쓴다는 사실만으로 느슨한 결합이 완성되지는 않습니다.
