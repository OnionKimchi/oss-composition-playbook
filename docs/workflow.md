# 개발 절차

## 1. 요구사항 정리

사용자가 해결하려는 업무, 사용자 수, 데이터 종류, 배포 장비, 비용 제약, 응답·가용성 요구를 정리합니다. 모르는 값은 가정으로 표시하고 설계를 바꾸는 질문부터 묻습니다.

## 2. 기능별 구현 방식 선택

각 기능을 기존 서비스 채택, 기존 서비스 확장, 직접 구현 중 하나로 제안합니다. 제품 이름부터 정하지 않습니다. 후보의 실제 API·라이선스·배포 요구를 공식 문서와 소스로 확인합니다. README의 홍보 문구만으로 적합 판정을 내리지 않습니다.

후보가 요구를 충족하는지, 도입 후 통합·운영 비용이 어떤지 비교합니다. 서비스 수를 줄일 수 있는 후보도 함께 고려합니다.

## 3. 경계 설계

메인 백엔드가 소유하는 규칙, 서비스별 기능, 원본 데이터, ID 매핑, 호출 계약, 인증과 실패 동작을 문서로 남깁니다. 내부 AI를 제안한다면 규칙 기반 처리와 비교해 필요한 이유를 설명하고 사용자와 결정합니다.

## 4. 최소 흐름 구현

사용자 입력 → 메인 백엔드 → 어댑터 → 외부 서비스 → 결과 표시의 한 흐름을 먼저 연결합니다. 초기에는 가짜 데이터나 테스트 데이터를 사용합니다. 모든 후보를 한꺼번에 배포할 필요는 없습니다.

## 5. 검증

- 정상 흐름의 입력과 최종 결과가 요구에 맞는지 확인합니다.
- 외부 서비스 중단·지연·권한 거부 때 사용자 결과를 확인합니다.
- 재시도되는 쓰기 요청이 중복 생성이나 잘못된 완료 상태를 만들지 확인합니다.
- 서비스 API 계약 변화가 어댑터에서 드러나는지 확인합니다.
- 데이터를 영속 저장하는 구성은 백업을 실제로 복원해 확인합니다.

수행한 명령·환경·결과와 미검증 항목을 기록합니다. 시험하지 않은 성능과 장애 격리를 보장하지 않습니다.

## 6. 배포와 인수인계

설정값, 비밀값 주입 방법, 볼륨, 백업·복구, 업그레이드·롤백 절차를 남깁니다. 개발 환경과 운영 환경의 차이를 표시합니다. 배포 브랜치나 CI 도입 여부는 프로젝트 상황에 따라 정합니다.

## 7. 유지보수

외부 제품 업데이트 시 API와 데이터 이전 영향을 확인합니다. 도입 당시의 선정 이유가 유효한지 재검토합니다. 서비스가 불필요해졌다면 연결과 데이터를 정리하고 제거합니다.
